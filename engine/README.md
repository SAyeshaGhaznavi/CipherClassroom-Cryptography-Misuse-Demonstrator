# CipherClassroom security engine (Member B)

This folder holds the security engine and the evaluation fixtures for
CipherClassroom. It is layer 3 and layer 5 of the architecture in the
proposal: the cryptographic logic itself, and the safe sample inputs the
tests run against.

It runs on its own. It does not need the frontend, a database, a server or
Docker, and it has no runtime dependencies at all. The only thing installed
is TypeScript and the Node type definitions, both of which are build time
only.

## Requirements

* Node.js 20 or newer (Node 22 LTS is what the frontend README recommends,
  and the same install covers this folder)
* npm
* VS Code, or any editor

## Running it

Open a terminal in this folder.

```powershell
cd engine
npm install
npm test
```

That compiles the TypeScript and runs 57 unit tests covering positive,
negative, edge case and misuse behaviour.

To run the seven mandatory evaluation cases and write the evidence report:

```powershell
npm run evaluate
```

This prints a pass or fail line per case and writes two files into
`reports/`: `evaluation-report.md` for the final report, and
`evaluation-report.json` for anyone who wants to process the results.

To walk the guided sequence in the order the specification sets out, which
is the script to run during the recorded demonstration:

```powershell
npm run demo
```

## How this fits the other two parts

The engine produces the exact `ExperimentResult` object that is already
written down in `docs/API_CONTRACT.md` and in
`frontend/src/lib/types.ts`. Nothing needs renaming on the way through. The
engine adds one extra field, `engine`, which carries the rule name, the
policy version, the thresholds that were applied and the reasons for the
decision. The specification asks for that information to be stored with
every result so a reviewer can reproduce the decision later. Anyone who
does not want it can drop the field and the rest still matches.

Member A calls `runExperiment(input, options)` and passes an
`onAuditEvent` callback. The engine hands back suggested audit events so
the repository layer can append them. The engine itself stores nothing.

Member C already has a demonstration engine inside the frontend for working
offline. That file is untouched. When the API is live, the frontend can
switch to real results without changing a single component, because the
shape is the same.

`docs/ENGINE_CONTRACT.md` in this folder has the call signatures and a
worked example for both.

## Security decisions, and why

**AES-256-GCM rather than AES-CBC.** GCM authenticates as well as encrypts.
With CBC, a modified ciphertext decrypts into different plaintext and the
caller has no way to tell. With GCM, the tag check fails and the message is
refused. The tampering test in T2 is only meaningful because the mode makes
it meaningful.

**PBKDF2 with a configurable cost rather than a bare SHA-256.** SHA-256 is
designed to be fast, which is the opposite of what password storage needs.
PBKDF2 makes each guess cost real time, and the cost is a number the lab can
move. T3 derives the same password at two costs and prints both timings so
the difference is measured rather than asserted.

**A fresh 96 bit nonce for every message, generated by the platform random
source.** The nonce reuse module is the one place that deliberately breaks
this rule, in isolation, with a key that is generated for that run and never
leaves memory. It also runs the same comparison with fresh nonces so the
leak can be attributed to the reuse and not to the cipher.

**A fresh 128 bit salt for every derivation.** Without a salt, one
precomputed table breaks every account that shares a password.

**Comparison that always inspects every byte.** `constantTimeEquals` in
`util/bytes.ts` does not return early on the first difference, because a
comparison that returns early leaks, through its own running time, how many
leading bytes matched.

**Thresholds in a policy object rather than as constants in the modules.**
An administrator can change one permitted value, repeat a test, and show
that the result and the configuration change are both traceable. Changing a
threshold moves the policy version forward, and the new version is written
into every result produced afterwards. T-final-d demonstrates exactly this.

**Validation before anything cryptographic runs.** Length, type, control
characters, parameter ranges and Unicode normalization are all checked
first, on the server side, and every rejection carries a stable code. The
engine never returns a stack trace or an internal path to a caller.

**No plaintext in the stored metadata.** Results record a 16 character
prefix of the SHA-256 digest of the normalized input. That is enough to tie
a stored result to the input that produced it, and not enough to recover the
input. There is a unit test that checks a supplied password does not appear
anywhere in the metadata.

## Limitations and ethics

The nonce reuse module implements an unsafe construction on purpose, for
teaching. It only ever operates on keys and nonces it generates itself,
inside the process, for the length of one call. It cannot be pointed at
anything external and it has no network access of any kind.

The classical cipher modules are teaching material. Nothing in here should
be used to protect real data, and the engine says so in the warning text it
returns rather than leaving the reader to work it out.

PBKDF2 was chosen because it is available in Web Crypto on every target
platform with no dependency to install. Argon2id would be the better choice
for new production systems, and that tradeoff belongs in the final report.

The timing figures in T3 are measured on whatever laptop runs them. They are
useful as a relative comparison between two costs on one machine, not as an
absolute claim about what an attacker with dedicated hardware could do.
